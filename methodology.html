方法论

这份文档记录：每个测量是怎么设计的、支撑它的证据是什么、以及哪些做法被否掉了。每条结论后面都附了可验证的方式——实测数字，或者文献名。

这份方法页回答什么

三十秒就能拿走结论，剩下的都是证据。

  1. 16 到 32 cm/360 之间，灵敏度对可测表现没有显著影响。五档各 30 球的对照实验，极差 5.8%，在噪声之内。别再花几个小时调它。
  2. 闭环任务测不出增益误差。你会在点击前修正，修正把误差抹平——落点分布永远居中。这是我们做了四版过冲法才接受的事。
  3. 步进任务能测出来。目标跳变后的前 ~100–150 ms 还没开始修正，响应幅度正比于增益；自检注入 0.85/1.00/1.15，读回 84%/99%/114%。
  4. 所以我们只报能量得准的东西：落点偏差、首段停点、哪一段慢（T1/T2）。「你的理想 cm/360 是多少」——明确不提供，因为它测不出来。

下面每一节都先给一句结论，再展开证据。失败的过程收在最后的附录里，不想看可以跳过。

灵敏度到底重不重要？

结论：在这个区间里，灵敏度对命中速度没有可测的影响——调它带来的收益小于测量噪声。

对照实验

五种灵敏度，各 30 球，分块顺序做平衡（后半程反向，用来抵消学习与疲劳漂移）：

cm/360   相邻两球中位间隔   中位重入次数
16       538 ms            1.0
20       551 ms            0.0
23.2     538 ms            0.0
27       521 ms            0.0
32       531 ms            0.0

极差 5.8%，在统计噪声之内。在这个区间里，灵敏度对命中速度没有可测的影响。这也解释了为什么有人能调几个小时灵敏度却感觉不出差别——效应比噪声还小。

开环这条路：三个模型，一次诚实的改判

结论：想从弹道里读出「你以为目标在哪」这条路走不通——三个模型都以同样的方式失败，拟合出的幅度把动作形状吸收了。

如果甩枪的前 250 ms 还是弹道的，那它的终点应该编码的是设置，而不是修正。为此做了三个模型，全部以同一种方式失败：拟合出的幅度把动作的形状吸收进去了。

v5 —— 指数上升，A·(1 − e−t/τ)

把已知增益 1.00 的最小急动度轨迹（真实动作的 S 形）喂进去：

动作时长   读出的增益
0.15 s     1.089
0.20 s     1.172
0.25 s     1.281

这个模型没有加速段，拿它拟合 S 曲线会把幅度抬高。

v6 —— 最小急动度，A·(10u³ − 15u⁴ + 6u⁵)

在干净的合成数据上正确到 ±1.6%，但在真实录制上，同一段动作指数模型读 0.88、这个模型读 1.33。A 和 D 在一条被截断的轨迹里不可分辨：更长更平的曲线，配一个更大的幅度，残差一样好。

v7 —— 首次停点，不做任何拟合

取速度掉到峰值 15% 以下那一刻的位置，不外推。端到端验证（把合成动作从页面真实的 pointermove 路径注入）：

注入增益   cm/360   读出
0.85       27.1     84%
1.00       27.1     99%
1.15       27.1     114%
1.00       40.0     99%

测量链准确到 ±1%，而且与灵敏度设置无关。

它到底测的是什么

链条既然证明是准的，剩下的读数就只能当真——而它稳定在 20° 时 71%、40° 时 71%（CI ±13–14%，统计上分不开）。纯增益误差也应该与距离无关，但调好的灵敏度会落在 100% 附近。71% 意味着第一段动作只走完了大约 71% 的距离，剩下的靠修正补上。

这才是人指点的两段式结构，不是灵敏度误差。所以这个页面从「开环标定」改名成「初段覆盖」，并且删掉了「建议 cm/360」和「应用到设置」——它们此前在制造漂移（每跑一轮就把 cm/360 乘上约 0.7）。

自检：在页面地址后面加 ?selftest=1，它会注入三个已知增益，报告这条测量链在你当前浏览器里还成不成立。

分轴定位（Axis-staged）

结论：把二维甩枪拆成「横移 → 纵向微调」两段，就能分别测出你慢在哪一段；ID 减半还顺带省掉约一个比特的运动时间。

目标：把二维的甩枪拆成两段，让每一段都能单独被测量。

1. 两成分动作，强行串行化

Woodworth（1899）把瞄准描述为「初始弹道冲击 + 二次修正」两个成分。斜向的二维甩枪里，两个成分同时发生，所以单一的「总用时」说不出是哪一段慢。

分轴定位强行规定顺序：先画一条水平带（横移，T1），准星一进带就变绿，之后只剩纵向微调（T2）。

可验证：结果页把 T1、T2 分别给出中位数。自适应随机 / 小球精度只报一个总用时和一个误差——同一次慢，可能是任意一段造成的。

2. 为什么 ID 减半很重要

Fitts（1954）：MT = a + b · ID，其中 ID = log2(2A / W)。

如果横移只需要走到带边，有效距离 A 减半，ID 就正好少了 1 bit，移动时间少掉一个 b。MacKenzie（1992）给出的斜率 b 大约 100–150 ms/bit（经典一维实验）。

可验证：实测里 T1（大范围横移）明显大于 T2（纵向微调），这正是「第二段 ID 更低」的预测。

3. 渐隐不是装饰，是必需的

指导假说（Salmoni、Schmidt & Walter 1984）：附加反馈能加快习得，但会制造依赖，一旦撤掉表现就掉下来。那条带就是这种附加反馈，所以它不能被永远保留，而是按阶梯渐隐：

A0  带 = 2.0 × 半径，实线
A1  带 = 1.6 × 半径，实线
A2  带 = 1.3 × 半径，虚线
A3  细线，目标出现 0.4 s 后淡出
A4  完全没有带，回到纯二维瞄准

规则：连续 5 次进带升一级；进带失败、或连续 2 次未命中降一级。

可验证：等级存在 localStorage["cs2at.axisFade"] 里（{level, enter, miss}），?axisLevel=0..4 可以钉住某一级做 A/B。

4. T1/T2 分诊——老项目做不到的事

老项目回答的是「多快、多准」，回答不了「时间花在哪一段」。两个总用时相同的人，瓶颈可能完全相反：一个横移慢、落点干净；一个横移快、进带后一直悬停。分轴把两者分开：

症状             读数                          建议
T1 > 800 ms      大范围横移太慢                先扫快，再减速
T2 > 260 ms      进带后还在修正                进带就停手，只上下微调
|纵向误差| > 0.6°  纵向控制是短板               横移到位后先压住垂直
可验证：每跑完一轮，window.__axisReport 会给出 {t1, t2, dy, hit, level, n}。

灵敏度探针

结论：闭环任务测不出增益误差，步进任务能测出来；一次会话最多分辨约 5% 的差异。

为什么闭环任务测不出增益误差

闭环指向里，视觉反馈会把误差抹平：不管增益是多少，玩家都会一直修正到准星落在目标上。于是落点分布永远居中，与设置无关（Powers 1973；Elliott 等 2010）。

我们自己的对照实验——五种灵敏度、各 30 球、分块顺序平衡：

cm/360   相邻两球中位间隔
16       538 ms
20       551 ms
23.2     538 ms
27       521 ms
32       531 ms

极差 5.8%，在测量噪声之内。同一个实验换个口径去测「首段覆盖」，得到的是 20° 时 71%、40° 时 71%——与距离无关，也就说明它读的是动作策略，不是设置。

为什么步进任务能测出来

目标跳变（step）会触发一次初始开环响应。前 ~100–150 ms 视觉反馈还来不及介入，所以响应的幅度正比于控制增益。把位移对跳变幅度做回归，就能直接得到增益，不需要任何模型（Woodworth 1899；Fitts & Peterson 1964；传递函数综述见 Argelaguet & Andujar 2013）。

可验证：初段覆盖页在 ?selftest=1 下自检，把 0.85 / 1.00 / 1.15 三个已知增益从真实指针路径注入，读回来是 84% / 99% / 114%——15% 的增益台阶，分辨率到 ±1%。

交错 A/B 的局限

把两个增益交错着练，会引发双重适应（Martin、Keating & Goodkin 1996）：两个内部模型互相竞争，测出来的差异被压小；而且每次切换后的 washout 会污染一块里的前几球。实际后果是功效上限：

每条件样本数 ≈ 2 (1.96 + 0.84)² (σ / δ)²，σ ≈ 10%
δ 5%  ->  约 63 球
δ 2%  ->  约 390 球
δ 1%  ->  约 1570 球

所以 60 球的 A/B 大约只能分辨 5%，30 球一块大约 7%，更小的差异在一次会话里和噪声没有区别。

时间能测到什么精度：采样率与帧间隔 P99

结论：本站报的是「输入采样率」和「帧间隔 P99」，不报「输入到显示的绝对延迟」——后者用浏览器测不准。

  • 输入采样率：用 pointerrawupdate 拿到未合并的指针事件（MDN：pointerrawupdate 提供未经浏览器合并的原始指针事件）。它决定你能分辨的最小时间粒度——1000 Hz 的鼠标，相邻两个样本至少隔 1 ms。
  • 帧间隔 P99：取 requestAnimationFrame 相邻时间戳之差，报第 99 百分位。均值会被少数长帧掩盖，P99 才代表「卡一下」的程度。
  • 为什么不用 rAF 算延迟：rAF 回调与垂直同步对齐（HTML 规范里渲染更新按刷新率调度），任何事件的耗时都会被吸附到 16.7 ms（60 Hz）或 8.3 ms（120 Hz）的栅格上。亚帧的差异进不了这个时间轴，所以拿它算「输入→显示」的绝对延迟，只会得到一个不存在的精度。
  • 事件时间戳同源：event.timeStamp 与 performance.now() 共享同一时间原点，可以相减；但两者都只表示「浏览器看到事件」的时刻，不含显示器扫描输出那一段。

不存在「真实灵敏度」

结论：「理想灵敏」不是一个客观存在的数值，它是映射与距离的函数；本站因此不提供这个数字。

1. 灵敏度是映射的属性，不是人的属性。所谓「最优」是相对于显示增益、以及你此刻面对的距离定义的；改动其中任何一个，最优值就会移动。我们的五档实验在 16–32 cm/360 之间没有找到可测差异（极差 5.8%，在噪声内）。

2. 可测信号由策略主导。首段覆盖在 20° 和 40° 都是 71%——与距离无关，改设置也不动它。真正的增益误差会跟着设置走，这个数不会。

3. 任何残余效应都低于一次会话的分辨率。要分辨 1% 需要每个条件约 1570 球；整个五档实验（5 × 30 = 150 球）只能分辨到约 10%。

所以站点报告的是这些，而不是一个「理想值」：

问题                        能测吗   我们报什么
我的落点是否系统性偏一侧？   能       点击偏差 + CI（点击偏差检查）
我的第一段停在哪？          能       初段覆盖（?selftest=1 证明链条）
我甩枪的哪一段慢？          能       T1 / T2 / 纵向误差（分轴定位）
我的理想 cm/360 是多少？     不能     明确不提供

结论

  1. 16 到 32 cm/360 之间，灵敏度对可测表现没有显著影响；不要在调它上面过度投入。
  2. 如果非要校准，用过冲法，但汇总样本、剔除命中、并且防漂移。
  3. 只用一个难度控制器，并且把目标定在 85% 成功率，否则反馈环会发散。
  4. 换硬件或改引擎之后感觉到的差别，多半来自重建肌肉记忆——只有重复能修。
  5. 点击任务测不出增益误差。闭环修正会把它抹掉；开环又拿掉了动作赖以规划的视觉信息。剩下能测的只有：第一段停在哪（初段覆盖）、落点是否系统性偏离（点击偏差）、以及哪一段慢（分轴定位）。
  6. 信任任何一个数字之前，先自检测量链。初段覆盖页在 ?selftest=1 提供自检；过不了自检的那一轮不该采信。

过冲法的四次迭代

v1 —— 记录点击位置

f       = (落点 - 目标) / 目标
cm_new  = cm * (1 + f)

问题：玩家在点击前就会视觉修正，记录到的位置已经是修正后的位置。每一轮只建议 3–8% 的改动，永远不收敛。

v2 —— 记录停稳位置（速度 < 25°/s 持续 70 ms）

观测到的最好收敛：

cm/360   过冲
23.2     +7.4%
24.9     +4.8%
26.1     +2.9%
26.9     +2.9%
27.7     +2.3%

单调下降；最后两轮只差 0.7%。

v3 —— 记录弹道终点（速度降到 40°/s 以下）

失败。这个点落在减速中段。散度约 ±15%，而要测的偏差只有约 5%，信噪比太低：

cm/360   过冲      过冲 : 欠冲
23.2     +8.7%     20 : 13
25.2     +16.0%    20 : 14
29.2     +3.3%     22 : 7
51.5     -0.7%     15 : 16

轮次之间符号都翻转过。

v4 —— 点击位置，剔除命中，汇总样本

  • 用点击位置（不需要等待停稳，和玩家的体感一致）
  • 剔除命中（角度误差在球半径内）：命中只说明「控制够用」，不代表「有偏差」
  • 把所有轮次的样本汇总，每个样本换算成它隐含的 cm/360，取全局中位数

结果：480 个样本收敛到 27.2 cm/360，最终偏差 −0.1%。

踩过的坑

1. 自动回填导致的漂移

「再测一轮」会自动填入建议值。数据有噪声时，每一轮都建议一点小改动，序列一路漂到荒谬的值（23.2 漂到 8.0，也就是转一整圈只要 8 cm）。

修法：改动超过 35% 时拒绝自动填入；加一个「清空样本池」按钮。

2. 限时里的死亡螺旋

允许时间 = 0.9 × 命中球用时的中位数
-> 只有快的尝试才算命中
-> 中位数下降
-> 允许时间下降
-> 超时更多，活下来的命中更快

实测命中率从 60% 掉到 30%、再掉到 25%，同时球半径还在变大——因为两个控制器在互相打架。

修法：

限时模式开 -> 球固定，只调允许时间
               命中率 >= 85%：收紧 6%
               命中率 <  70%：放宽 7%
限时模式关 -> 时间固定，只调球的大小

3. 视觉大小和命中判定不一致

球按 1.5° 半径画，命中判定却用甩枪距离的 3%（约 0.6°）。玩家看着准星明明在球里，却判成未命中。

修法：命中判定直接用角度误差和画出来的半径比。

4. 角度没有归一化

// 错
Math.abs(tYaw - yaw);      // 目标 179°，当前 -179° -> 358°

// 对
wrapPi(tYaw - yaw);        // -> 2°

症状：「往一个方向转过去之后，就再也打不中了」。累计转动越过 ±180° 之后，判定永远不可能通过。

5. tan() 在 90° 处翻号

目标的世界坐标原本用 x = D * tan(yaw) 算，越过 ±90° 会翻号，球被画到镜像的位置上。

正确的球面定位：

const x = D * Math.cos(pitch) * Math.sin(yaw);
const y = D * Math.sin(pitch);
const z = D * Math.cos(pitch) * Math.cos(yaw);

6. 同步写盘会把输入报告合并掉

一个原始输入记录器如果每个 HID 报告都 WriteLine + AutoFlush，会堵住消息循环，Windows 就开始合并 WM_INPUT：

同步写盘     -> 实测 124 Hz
内存缓冲     -> 实测 4207 Hz

同一只 8K 鼠标，差 34 倍。测回报率之前，先排除这一项。

Methodology

This document records how each measurement was designed, what evidence backs it, and which approaches were rejected. Every claim carries a way to check it — a measured number, or a citation.

What this page answers

Thirty seconds gets you the conclusions; everything after is the evidence.

  1. Between 16 and 32 cm/360, sensitivity has no measurable effect on performance. Five conditions, thirty trials each — spread 5.8%, inside the noise. Stop tuning it.
  2. Closed-loop tasks cannot measure a gain error. You correct before clicking, and the correction erases the error — the landing distribution stays centred. It took us four versions of the overshoot method to accept that.
  3. A step task can. For the first ~100–150 ms after a target jump there is no correction yet, so the response amplitude is proportional to the gain; injecting 0.85 / 1.00 / 1.15 reads back 84% / 99% / 114%.
  4. So we report only what can be measured: landing bias, first-stop coverage, and which stage is slow (T1/T2). “Your ideal cm/360” is deliberately not offered, because it cannot be measured.

Each section below opens with its conclusion in bold, then the evidence. The failed attempts are collected in the appendix at the end — skip them if you just want the method.

The open-loop detour: three models, one honest reframe

Conclusion: reading “where you think the target is” out of the ballistic path does not work — all three models failed the same way, with the fitted amplitude swallowing the shape of the movement.

If the first 250 ms of a flick is still ballistic, its endpoint ought to encode the setting rather than the correction. Three models were built. All failed the same way: the fitted amplitude absorbed the shape of the movement.

v5 — exponential rise, A·(1 − e−t/τ)

Synthetic minimum-jerk trajectories (the realistic S-shape) with a known gain of 1.00:

The model has no acceleration phase, so fitting it to an S-curve inflates the amplitude.

v6 — minimum-jerk, A·(10u³ − 15u⁴ + 6u⁵)

Correct on clean synthetic data to ±1.6%, but on a real recording the same motion read 0.88 with the exponential and 1.33 with this model. A and D are not separately identifiable from a truncated trajectory: a longer, flatter curve fits equally well with a larger amplitude.

v7 — first stop, no model at all

Take the position at the moment speed falls below 15% of its peak — no extrapolation. Validated end-to-end, with synthetic motion injected through the page’s own pointermove path:

The chain is accurate to ±1% and independent of the sensitivity setting.

What it actually measures

With the chain proven, the remaining readings had to be believed — and they sat at 71% at 20° and 71% at 40° (CI ±13–14%, statistically indistinguishable). A pure gain error would also be distance-invariant, but a correctly tuned sensitivity would land near 100%. 71% means the first movement covers only about 71% of the distance and a correction supplies the rest.

That is the two-phase structure of human pointing, not a sensitivity error. The page was renamed from “open-loop calibration” to first-move coverage, and its “suggested cm/360” and “apply to settings” controls were removed — each run was multiplying cm/360 by about 0.7.

Axis-staged positioning

Conclusion: splitting a 2-D flick into transport and vertical micro-adjustment makes it possible to measure which stage is slow — and halving the effective distance saves roughly one bit of movement time.

Goal: split a 2-D flick into its two stages so each can be measured separately.

1. A two-component movement, forced to serialize

Woodworth (1899) described aiming as an initial ballistic impulse followed by a corrective secondary movement. In a diagonal 2-D flick both components happen at once, so a single “time to hit” cannot say which one was slow.

Axis-staged forces the order: a horizontal band is drawn first (transport, T1), and once the crosshair is inside the band it turns green and only a vertical fine adjustment remains (T2).

Verifiable: the result page reports T1 and T2 as separate medians. The random / precision drills report one total time and one error — the same slow run could be either stage.

2. Why halving the ID matters

Fitts (1954): MT = a + b · ID, with ID = log2(2A / W).

If the transport only has to reach the band, the effective distance A halves, so the ID drops by exactly one bit, and movement time falls by b. MacKenzie (1992) puts the slope b at roughly 100–150 ms/bit in the classic 1-D studies.

Verifiable: in our runs T1 (gross sweep) sits well above T2 (fine adjust), which is what a lower-ID second stage predicts.

3. Fading the guide is necessary, not cosmetic

The guidance hypothesis (Salmoni, Schmidt & Walter 1984): augmented feedback speeds up acquisition but creates a dependency, and performance falls away once it is removed. The band is exactly that guidance, so it is faded on a ladder instead of being kept forever:

A0  band = 2.0 x radius, solid
A1  band = 1.6 x radius, solid
A2  band = 1.3 x radius, dashed
A3  thin line, fades 0.4 s after the target appears
A4  no band at all - plain 2-D aiming

Rule: five consecutive band entries upgrade a level; a failed entry, or two consecutive misses, downgrades one.

Verifiable: the level lives in localStorage["cs2at.axisFade"] as {level, enter, miss}, and ?axisLevel=0..4 pins it for an A/B.

4. T1/T2 triage — what the older drills cannot do

The older drills answer “how fast and how accurate”; they cannot answer “which stage costs you the time”. Two players with the same total time can have opposite bottlenecks: one sweeps slowly and lands cleanly, the other sweeps fast and then hovers. Axis separates them:

symptom          reading                          advice
T1 > 800 ms      the gross sweep is slow          move faster first, then settle
T2 > 260 ms      still correcting after arrival   stop on entry, adjust vertically only
|dy| > 0.6 deg   vertical control is the weak link lock vertical before clicking
Verifiable: window.__axisReport exposes {t1, t2, dy, hit, level, n} after every run.

The sensitivity probe

Conclusion: closed-loop tasks cannot see a gain error, step tasks can, and one session resolves at best about 5%.

Why a closed-loop task cannot measure a gain error

In closed-loop pointing the visual feedback nulls the error: whatever the gain, the player keeps correcting until the crosshair is on the target. The endpoint distribution is centred at zero no matter what the setting is (Powers 1973; Elliott et al. 2010).

Our own controlled run — five sensitivities, thirty trials each, block order counterbalanced:

cm/360   median ball-to-ball interval
16       538 ms
20       551 ms
23.2     538 ms
27       521 ms
32       531 ms

The spread is 5.8%, inside the noise of the measurement. The same experiment run as a first-move estimate gives 71% at 20° and 71% at 40° — distance-invariant, which means it is reading the movement strategy, not the setting.

Why a step task can

A step (the target jumps) triggers an initial open-loop response. For the first ~100–150 ms visual feedback cannot act, so the response amplitude is proportional to the control gain. Regressing displacement on the step size recovers that gain directly, with no model to fit (Woodworth 1899; Fitts & Peterson 1964; Argelaguet & Andujar 2013 for the transfer-function review).

Verifiable: the first-move page self-checks with ?selftest=1, injecting known gains of 0.85 / 1.00 / 1.15 through the real pointer path — it reads back 84% / 99% / 114%, so a 15% gain step is resolved to ±1%.

Limits of interleaved A/B

Interleaving two gains invites dual adaptation (Martin, Keating & Goodkin 1996): the two internal models compete, the measured difference shrinks, and washout after each switch biases the first trials of a block. The practical consequence is a power limit:

n per condition ~= 2 (1.96 + 0.84)^2 (sigma / delta)^2,  sigma ~ 10%
delta 5%  ->  ~63 trials
delta 2%  ->  ~390 trials
delta 1%  ->  ~1570 trials

So a 60-ball A/B can resolve about 5%, a 30-ball block about 7%, and anything smaller is indistinguishable from noise in one session.

What the timing can actually measure: sampling rate and frame-interval P99

Conclusion: this site reports the input sampling rate and the frame-interval P99 — never an absolute input-to-display latency, because a browser cannot measure that honestly.

  • Input sampling rate. pointerrawupdate delivers pointer events before the browser coalesces them (MDN: pointerrawupdate fires for raw, un-coalesced pointer events). It sets the smallest time step you can resolve — a 1000 Hz mouse gives one sample every 1 ms at best.
  • Frame-interval P99. Take the differences between consecutive requestAnimationFrame timestamps and report the 99th percentile. A mean hides the few long frames; P99 is what tells you how bad the stutter is.
  • Why rAF cannot give a latency. Animation-frame callbacks are aligned to vertical sync (the HTML rendering update is scheduled at the refresh rate), so every event cost snaps to the 16.7 ms (60 Hz) or 8.3 ms (120 Hz) grid. Sub-frame differences never enter that timeline, so an “input-to-display latency” computed from rAF is precision that does not exist.
  • Timestamps share one origin. event.timeStamp and performance.now() are on the same time origin and can be subtracted — but both mark when the browser saw the event; neither includes display scan-out.

There is no such thing as a “true” sensitivity

Conclusion: an “ideal sensitivity” is not an objective number — it is a function of the mapping and the distances you face, which is why the site does not offer one.

1. Sensitivity is a property of the mapping, not of the player. The optimum is defined relative to the display gain and to the distances you happen to face; change either and the optimum moves. Our five-condition experiment found no measurable difference from 16 to 32 cm/360 (spread 5.8%, inside noise).

2. The measurable signal is dominated by strategy. First-move coverage is 71% at 20° and 71% at 40° — distance-invariant, and unchanged when the setting changes. A real gain error would track the setting; this number does not.

3. Any residual effect is below the resolution of a session. Detecting 1% needs about 1570 trials per condition; the entire five-condition experiment (5 × 30 = 150 trials) can only resolve about 10%.

What can be measured, and what the site therefore reports instead:

question                                  measurable?   what we report
is my landing systematically off-centre?  yes           click bias + CI (click-bias checker)
where does my first movement stop?        yes           first-move coverage (?selftest=1)
which stage of the flick is slow?         yes           T1 / T2 / vertical error (axis-staged)
what is my ideal cm/360?                  NO            deliberately not offered

The other measurement tools

Conclusion: each tool reports only what it can prove, and stays silent about the rest.

Same principle: each tool reports only what it can prove.

tool             what it measures                    key parameters / criteria
Check-up         reaction, first shot, confirmation,  fixed 90 s recipe (micro / wide / mid cycle),
                 micro-adjust, wide flick, stability  the first 6 shots are warm-up and not scored

                                                     of the reversal points

The six check-up dimensions map to: reaction (time to first movement), first shot (where the first sub-movement lands), confirmation (interval from the first stop to the shot), micro-adjust (hit rate on small angles), wide flick (hit rate and time on large angles), stability (hit-rate difference between the first and the second half of the run).

Staircase and random distance reuse the same spawn / judge / finish pipeline as every other mode; only the recorded fields differ. Staircase pins the distance at 18° so that size is the only variable, and random distance pins the size at 1.5° so that distance is the only variable — two variables moving at once would make neither number interpretable.

Conclusions

  • Sensitivity between 16 and 32 cm/360 has no significant effect on measured performance; do not over-invest in tuning it.
  • If you calibrate, use the overshoot method, but pool samples, exclude hits, and guard against drift.
  • Use a single difficulty controller and an 85% success target, otherwise the feedback loop diverges.
  • Most of the felt difference after a hardware or engine change comes from rebuilding motor memory, which only repetition can fix.
  • Pointing tasks cannot measure gain error. Closed-loop correction erases it; opening the loop removes the information the movement is planned from. What remains measurable is where the first movement stops (first-move coverage) and whether the landing is systematically off-centre (click bias).
  • Verify the measuring chain before trusting a number: the open-loop page self-checks at ?selftest=1.

    • Appendix: how we got here

    This section records the process, not the conclusions. If you only want the method, skip it.

    Four iterations of the overshoot method

    v1 — record the click position

    
f       = (landing - target) / target
cm_new  = cm * (1 + f)

    Problem: players visually correct before clicking, so the recorded position is already the corrected one. Each round suggested only a 3-8% change and never converged.

    v2 — record the settled position (speed < 25°/s for 70 ms)

    Best convergence observed:

    
cm/360   overshoot
23.2     +7.4%
24.9     +4.8%
26.1     +2.9%
26.9     +2.9%
27.7     +2.3%

    Monotonic decrease; the last two rounds differed by 0.7%.

    v3 — record the ballistic endpoint (speed dropping below 40°/s)

    Failed. This captures a point mid-deceleration. Scatter was about ±15% while the bias being measured was about 5%, so the signal-to-noise ratio was too low:

    
cm/360   overshoot   overshoots : undershoots
23.2     +8.7%       20 : 13
25.2     +16.0%      20 : 14
29.2     +3.3%       22 : 7
51.5     -0.7%       15 : 16

    The sign flipped between rounds.

    v4 — click position, hits excluded, pooled samples

  • Use the click position (zero latency, matches what the player feels)
  • Exclude hits (angular error within ball radius) from the bias estimate: a hit means "control was sufficient", not "there was a bias"
  • Pool every trial across runs, convert each to the cm/360 it implies, take the global median

    • Result: 480 samples converged to 27.2 cm/360 with a final bias of -0.1%.

    Pitfalls encountered

    1. Auto-fill drift

    "Run again" filled the suggested value automatically. With noisy data each round suggested a small change, and the sequence drifted to an absurd value (23.2 to 8.0, i.e. 8 cm per full turn).

    Fix: refuse to auto-fill when the change exceeds 35%; add a "clear pool" button.

    2. Death spiral in the time limit

    
allowed time = 0.9 * median of HIT times
-> only fast attempts count as hits
-> the median falls
-> the allowed time falls
-> more timeouts, the surviving hits are faster still

    Measured hit rate fell 60% -> 30% -> 25% while the ball radius grew, because two controllers were fighting.

    Fix:

    
time-limit mode on  -> ball fixed, only the time limit adapts
                       hit rate >= 85%: tighten 6%
                       hit rate <  70%: relax 7%
time-limit mode off -> time fixed, only the ball adapts

    3. Visual size did not match the hit test

    The ball was drawn at a 1.5° radius while the hit test used 3% of flick distance (about 0.6°). Players saw the crosshair inside the ball and still registered a miss.

    Fix: the hit test compares angular error directly against the drawn radius.

    4. Angles were not wrapped

    
// wrong
Math.abs(tYaw - yaw);      // target 179°, current -179° -> 358°

// correct
wrapPi(tYaw - yaw);        // -> 2°

    Symptom: "after I turn one direction I can no longer hit anything". Once accumulated rotation passed ±180° the test could never pass.

    5. `tan()` flips at 90°

    Target world position was computed as `x = D * tan(yaw)`, which flips sign past ±90°, drawing the ball at a mirrored position.

    Correct spherical placement:

    
const x = D * Math.cos(pitch) * Math.sin(yaw);
const y = D * Math.sin(pitch);
const z = D * Math.cos(pitch) * Math.cos(yaw);

    6. Synchronous disk writes merge input reports

    A raw-input logger that calls `WriteLine` + `AutoFlush` per HID report blocks the message loop, and Windows begins coalescing `WM_INPUT`:

    
synchronous writes   -> measured 124 Hz
memory buffering     -> measured 4207 Hz

    A 34x difference on the same 8K mouse. Always rule this out before measuring polling rate.
